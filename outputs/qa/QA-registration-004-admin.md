# 报名管理 测试用例

| 用例编号 | 关联 AC/校验规则 | 前置条件 | 操作步骤 | 预期结果 |
|---|---|---|---|---|
| QA-registration-004-admin-001 | AC-001 | 某报名记录状态为"未签到" | 点击"签到" | 状态变为"已签到"，"已签到"统计数字 +1 |
| QA-registration-004-admin-002 | AC-001 | 某报名记录状态为"已签到" | 点击"撤销签到" | 状态变为"未签到"，"已签到"统计数字 -1 |
| QA-registration-004-admin-003 | AC-002 | 某报名记录状态为"未签到" | 点击"取消报名" | 原地展示二次确认提示；确认后该记录从列表移除，"已报名"统计 -1，"已签到"统计不变 |
| QA-registration-004-admin-004 | AC-002 | 某报名记录状态为"已签到" | 点击"取消报名"并确认 | 该记录从列表移除，"已报名"与"已签到"统计同时 -1 |
| QA-registration-004-admin-005 | AC-003 | 手动添加代报名表单已打开，已选择所属 Celebration | 姓名留空，点击提交 | 阻止提交并提示 |
| QA-registration-004-admin-006 | AC-003 | 手动添加代报名表单已打开，已选择所属 Celebration | 填写姓名（部门留空），提交 | 新记录出现在列表最上方并标注所属 Celebration，"已报名"统计 +1，表单自动清空并收起，该记录部门展示"—" |
| QA-registration-004-admin-007 | §8 校验 | 用户端报名表单 | 填写手机号为非 11 位数字后提交 | 服务端拒绝，报名不生效（此规则发生于用户端，本用例验证服务端校验生效） |
| QA-registration-004-admin-008 | AC-004 | 员工在用户端某个 Celebration 完成一次报名 | 打开管理端报名名单 | 该条记录可被查询到，归属正确的 Celebration，与用户端提交的信息一致（前后端数据一致） |
| QA-registration-004-admin-009 | §9 五态-loading | 模拟报名名单接口响应延迟 | 打开报名管理页面 | 展示骨架屏 |
| QA-registration-004-admin-010 | §9 五态-empty | 该 Celebration 尚无人报名 | 打开报名管理页面 | 展示"该 Celebration 尚无人报名"文案，统计数字均为 0 |
| QA-registration-004-admin-011 | AC-005 | 报名名单中存在归属不同 Celebration 的记录 | 打开报名管理列表（不筛选） | 每一行均展示其所属 Celebration 名称 |
| QA-registration-004-admin-012 | AC-005 | 报名名单已加载多条不同 Celebration 的记录 | 选择某个 Celebration 筛选 | 仅展示该 Celebration 的记录，切换筛选立即生效 |
| QA-registration-004-admin-013 | §8 校验 | 手动添加代报名表单已打开 | 未选择所属 Celebration，点击提交 | 阻止提交并提示需选择 Celebration |
| QA-registration-004-admin-014 | §6 数据对象（报名信息模块配置） | 某 Celebration 的报名信息模块已设置名额上限 | 查看该 Celebration 的报名统计区域 | 名额上限数值正确展示；报满后的拦截行为暂不校验（见 §11 已知缺口） |
| QA-registration-004-admin-015 | AC-006 | 用户端报名弹窗已打开，联系电话已填合法值 | 邮箱留空，点击"确认报名" | 被阻止并提示邮箱必填，不报名 |
| QA-registration-004-admin-016 | AC-006 | 同上 | 邮箱分别输入"abc"、"a@b"、"@x.com"、"a@@b.com"、含空格的"a b@x.com" | 五种都提示邮箱格式不正确，报名被阻止 |
| QA-registration-004-admin-017 | AC-006（边界） | 同上 | 邮箱输入恰好 100 个字符的合法地址，再输入 101 个字符的 | 100 个字符的通过；101 个字符的被阻止并提示过长 |
| QA-registration-004-admin-018 | AC-006 / AC-004 | 同上 | 电话与邮箱都填合法值，点击"确认报名" | 报名成功；管理端报名名单中该记录出现，邮箱与所填一致，归属正确的 Celebration |
| QA-registration-004-admin-019 | AC-006 | 联系电话与邮箱都填了不合法的值 | 点击"确认报名" | 两处错误一并提示（电话格式、邮箱格式），不是只提示第一个；报名被阻止 |
| QA-registration-004-admin-020 | AC-006 / §8 校验（后端） | 直接调用员工自主报名接口 | 分别不传邮箱、传非法格式、传 101 个字符的邮箱 | 三种请求都被后端拒绝并返回明确原因，不产生报名记录 |
| QA-registration-004-admin-021 | AC-007 | 管理端报名名单中有员工自主报名和行政代报名（未填邮箱）两类记录 | 查看名单 | 新增"邮箱"列；员工自主报名的记录显示其邮箱；代报名未填邮箱的显示"—" |
| QA-registration-004-admin-022 | AC-008 | 手动添加代报名表单已打开，姓名已填 | 邮箱留空，点击"添加报名" | 添加成功，名单中该记录邮箱显示"—" |
| QA-registration-004-admin-023 | AC-008 | 同上 | 邮箱填"abc"，点击"添加报名" | 被阻止并提示邮箱格式不正确；改成合法邮箱后可添加，名单显示该邮箱 |
| QA-registration-004-admin-024 | AC-009 | 某 Celebration 名额上限 50，当前报名人数 50，员工尚未报名 | 员工打开用户端详情页 | 「立即报名」按钮文案变为「报名人数已达上限」，置灰；点击不会打开报名弹窗 |
| QA-registration-004-admin-025 | AC-009（边界） | 名额上限 50，当前报名人数 49 | 员工 A 打开详情页并报名，随后员工 B 打开详情页 | A 报名前按钮是「立即报名」；A 报名成功后人数为 50，B 看到「报名人数已达上限」 |
| QA-registration-004-admin-026 | AC-010 | 名额已满（50/50），员工 B 看到「报名人数已达上限」 | 另一位已报名的员工取消报名，B 刷新详情页 | 人数变为 49，B 看到的按钮恢复为「立即报名」，可正常报名 |
| QA-registration-004-admin-027 | AC-009 | 某 Celebration 名额上限留空，已有大量报名 | 员工打开详情页 | 按钮始终是「立即报名」，不出现「报名人数已达上限」 |
| QA-registration-004-admin-028 | AC-009 | 名额已满，某员工本人已经报名 | 该员工打开详情页 | 按钮显示「已报名 ✓」（置灰），而不是「报名人数已达上限」 |
| QA-registration-004-admin-029 | AC-009 | 名额上限 50，其中 10 条是行政手动代报名，员工自主报名 40 条 | 员工打开详情页 | 总人数 50 已达上限，按钮显示「报名人数已达上限」（代报名计入人数） |
| QA-registration-004-admin-030 | AC-011 / §8 校验（后端） | 名额已满 | 员工绕过页面，直接调用报名接口 | 请求被后端拒绝并返回「报名人数已达上限」，报名名单和人数不变 |
| QA-registration-004-admin-031 | AC-011（并发） | 名额上限 50，当前 49，两位员工同时打开报名弹窗 | 两人几乎同时点击「确认报名」 | 只有一人报名成功，另一人收到「报名人数已达上限」；最终报名人数为 50，不超额 |
| QA-registration-004-admin-032 | AC-009 | 名额已满 | 查看按钮及页面其他位置 | 按钮文案准确为「报名人数已达上限」；页面不显示名额的具体数字（上限值、剩余数） |
| QA-registration-004-admin-033 | AC-012 | 管理端报名名单中有员工自主报名和行政代报名两类记录 | 打开报名管理列表 | 表格新增"联系电话"列；员工自主报名的记录显示其填写的手机号 |
| QA-registration-004-admin-034 | AC-012 | 手动添加代报名表单已打开，姓名已填 | 联系电话留空，点击"添加报名" | 添加成功，名单中该记录联系电话显示"—" |
| QA-registration-004-admin-035 | AC-012 | 同上 | 联系电话填"+81 90-1234-5678"（带国家码和连字符），点击"添加报名" | 添加成功且不报格式错误，名单中该记录联系电话显示所填内容 |
| QA-registration-004-admin-036 | AC-012 / AC-004 | 员工在用户端以手机号 13800138000 报名成功 | 管理端打开该 Celebration 的报名名单 | 该记录的联系电话列显示 13800138000，与用户端所填一致 |
| QA-registration-004-admin-037 | AC-012 / §7 权限 | 非行政的员工账号 | 在用户端查看报名相关页面 | 任何位置都看不到其他人的联系电话 |
| QA-registration-004-admin-038 | AC-013 | 某 Celebration 名额上限 2，当前已报名 2（含 1 条行政代报名），管理端手动添加表单已打开，所属 Celebration 选该站 | 填写姓名，点击"添加报名" | 被阻止并提示"报名人数已达上限，无法再添加报名"；名单和已报名统计不变 |
| QA-registration-004-admin-039 | AC-013 / §8 校验（后端） | 同上 | 绕过页面，直接调用代报名接口 | 请求被后端拒绝并返回"报名人数已达上限"，不产生记录 |
| QA-registration-004-admin-040 | AC-013 | 同上，名额已满 | 先取消其中一条报名，再添加代报名；或把名额上限调大后再添加 | 两种方式之后都可以成功添加，人数不超过当前名额上限 |
| QA-registration-004-admin-041 | AC-013（边界） | 名额上限 2，当前 1 条 | 添加 1 条代报名，再添加第 2 条 | 第 1 条成功（人数变为 2）；第 2 条被阻止；已签到与未签到的记录都计入人数 |
| QA-registration-004-admin-042 | AC-013 | 名额上限留空（不限） | 连续添加多条代报名 | 全部成功，不触发"已达上限" |
