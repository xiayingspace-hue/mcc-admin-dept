# 产品上下文仓 · 模板

> **一句话说明**：产品经理一个人，用这个仓库把「一句话想法」变成**产品说明文档**和**可点击原型**——文档给开发照着做，原型给用户点着聊。

前后端由开发自行实现，本仓不管技术方案。

---

## 🎯 这个仓库为什么长这样

产品经理的两个真实瓶颈：

| 瓶颈 | 这里怎么解 |
|------|-----------|
| 写需求慢，且总漏东西（权限分支、异常、非功能需求） | `templates/` 定死必备章节，`rules/` 让 agent **先提问再落笔**，漏项在生成时就被拦住 |
| 画原型慢，画完还是说不清交互 | `prototypes/_shared/` 是一套现成的设计系统，agent 只填内容不做设计；**交互标注直接回指 AC 编号** |

三条设计判断：

1. **原型是一等公民，不是草稿。** 它是需求文档的表现形式，和文档双向可追溯——原型上每个红点标注都回指一条 AC。
2. **接口清单必须早于原型。** 否则原型里编的字段名和后面对不上，返工成本落在开发身上。
3. **只放跨角色的东西。** 只有开发自己读、且能从代码生成的内容（表结构、组件、路由约定）不进本仓——放进来只会过期且没人发现。

## 🔄 生成链路

```
一句话想法
   │  /req      ← agent 先提问补全缺口（最多 4 题），再落文档
   ▼
requirements/<端侧>/shared/<模块>-<编号>-<端侧>.md       业务规则主体
requirements/<端侧>/<载体>/<模块>-<编号>-<端侧>-<载体>.md  只写载体差异
   │
   ├─ /api   ─▶ outputs/api/API-…md          字段与枚举
   │              └─── 原型 mock 数据的形状依据 ───┐
   ├─ /proto ─▶ prototypes/….html  ◀──────────────┘   给用户点
   └─ /qa    ─▶ outputs/qa/QA-….md                    从 AC 派生
```

**方向单向**：需求变了，下游三样重新生成；下游发现问题，回头改需求，不在下游打补丁。

## 🧭 两根轴：端侧 × 载体

需求不按「页面」平铺，按 **端侧（谁用、走哪套 API）× 载体（跑在什么设备）** 组织。

| 轴 | 取值 | 含义 |
|----|------|------|
| **端侧** | `admin` / `user` | 管理端走 `/admin-api`，用户端走 `/app-api` |
| **载体** | `pc` / `native` / `h5` | 桌面浏览器 / 原生 APP / 移动网页 |

取值在 `background/product-overview.md` 登记，**按需创建目录**——只做管理端就不建 `user/`。

**写作分工（最重要的一条）**

| 位置 | 写什么 |
|------|--------|
| `requirements/shared/` | 全系统级：角色、术语 |
| `<端侧>/shared/` | **业务规则主体**：流程、状态机、权限、校验、数据对象、AC |
| `<端侧>/<载体>/` | **只写差异**：布局、手势、载体特有能力（扫码 / 微信授权 / 批量选择） |

没有载体差异就不建那个文件。建一个只写「同 shared」的空壳，是纯负债。

## 🏷️ 命名与编号

```
需求文档   <模块>-<编号>-<端侧>[-<载体>].md      employee-001-admin-pc.md
派生文档   <类型>-<模块>-<编号>-<端侧>.md         API-employee-001-admin.md
原型       <模块>-<编号>-<端侧>-<载体>.html      employee-001-admin-pc.html
```

- **编号三位、全局递增、永不复用、永不重编**。它是全链路追溯锚点，正文中以 `REQ-001` 引用。
- 模块归属变了只改 slug 段，编号与所有引用保持有效。
- 一次 `grep -rn "employee-001"` 捞出全仓相关文档。
- 不用 `001A` / `001B`，拆分直接分配新编号，依赖关系写进 `versions.md` 的依赖树。

模块 slug：小写 kebab-case、≤10 字符、**命名业务域而非功能动作**（`drawing` 不是 `upload-drawing`）、总数 ≤10 个、须先在 `GLOSSARY.md` 登记。

详见 [`rules/global-rules.md`](rules/global-rules.md)。

## 🎨 原型能力

`proto.css` + `tokens.css` + `proto.js` 提供一套现成的设计系统，agent 只填内容不做设计——**原型之间视觉一致，评审时注意力落在交互上，而不是「这版怎么又换风格了」**。

视觉分三层：`tokens.css` 是产品的品牌 token（前端更新时**整份覆盖**即可同步），`proto.css` 是组件骨架（只做「内部语义名 → 品牌 token」的映射，带 fallback，token 缺席时仍可独立工作），原型 HTML 只填内容。

| 能力 | 写法 |
|------|------|
| 多页面装进一个文件 | `<section class="p-screen" id="detail" data-title="员工详情">` |
| 点击跳转 | `<button data-goto="detail">` |
| 状态切换 | `<div data-when="empty">`，右下角控制台一键切 |
| 弹窗 / 提示 | `data-open="id"` / `data-close` / `data-toast="保存成功"` |
| 交互标注 | `<span class="anno" data-note="AC-003：手机号脱敏">3</span>` |
| PC 骨架 | 左侧导航 + 顶栏 + 内容 |
| 移动骨架 | 手机框并排展示，一屏看完整个流程 |

**五种状态硬性要求**——凡是要拉数据的页面：

| `normal` | `loading` | `empty` | `error` | `noperm` | `overflow` |
|---|---|---|---|---|---|
| 真实感假数据 | 骨架屏 | 分「从没有过」和「筛选无果」 | 原因 + 重试 | 分整页拦截和字段脱敏 | 超长文本不塌陷 |

只画正常态的原型，等于把最难的部分留给开发猜。

## 🧱 文档职责边界

> **每一类事实只在一处定义，其余文档一律引用。**
> 判断某段内容该不该写在这里，只问一句——**这个问题只有它能回答吗？**

| 文档 | 它独占回答的问题 |
|------|----------------|
| 产品需求 | 要做什么、为什么、什么情况下算对 |
| HTML 原型 | 长什么样、怎么点、每个状态显示什么 |
| 接口清单 | 前后端之间传什么字段、枚举有哪些值 |
| QA 用例 | 怎么证明它做对了 |

### 三个最容易重复定义的横切事实

| 事实 | 需求里写 | 接口清单里写 | 留给开发 |
|------|---------|------------|---------|
| **数据对象** | 业务含义：是什么、谁能看、何时变 | 传输形态：字段名 / 类型 / 枚举 | 持久化：表、索引、约束 |
| **权限** | 谁能做什么（**唯一定义处**） | — | 前端怎么藏、后端怎么拦 |
| **校验** | 规则是什么（**唯一定义处**） | 类型与长度约束 | 何时提示、强制执行 |

「数据对象」尤其要分清：产品定义的是**业务语义上的对象**（"员工有任职记录、有在职状态、薪资只有薪酬角色可见"），不是字段清单。字段名和类型属于接口清单，表结构属于开发。**三层同名不同物，混写是这类体系最常见的塌方点。**

### 什么不进本仓

判据：**几个角色读。** 只有一个角色读的文档，住那个角色的工作场所。

| 内容 | 归属 |
|------|------|
| design token 值、组件实现、路由约定、状态管理 | 前端仓 |
| 表结构、索引、事务边界、幂等实现 | 代码本身（migration / schema 即事实源） |
| 部署、环境、监控 | 运维仓 |

---

## ⚠️ 两个务必知道的边界

**接口清单是草案，不是契约。** 字段名、类型、枚举最终由后端定。这份清单的职责是「把 PM 脑子里的字段讲清楚」，让原型有形状、开发少问几轮——**不是约束后端**。后端实现后有出入，回来把清单改成实际的样子。

**原型不是生产代码。** 开发照着它实现，不复用它的 HTML。所以它可以写得直白：写死的假数据、内联的一切都没问题。唯一不可妥协的是——**原型上每个字段名和枚举值必须与接口清单一致**。

## 📐 设计原则

| 原则 | 说明 |
|------|------|
| **单一事实源** | `requirements/` 是唯一权威，其余全部从它派生 |
| **跨角色才入仓** | 只有一个角色读的内容住那个角色的仓库 |
| **端侧优先** | 业务规则写在 `<端侧>/shared/`，载体目录只承载差异 |
| **契约先行** | 先出字段清单，再画原型，mock 数据才有依据 |
| **追溯闭环** | AC → 原型标注 → 接口字段 → QA 用例，靠编号全链路串联 |
| **五态齐全** | 正常 / 加载 / 空 / 错误 / 无权限，缺一个就是留给开发的坑 |
| **语义引用** | 文档写 `"主色"`，不写 `#2f6fed`；色值只存在于 proto.css |
| **不留待定** | 未定项写进「已知缺口」并注明谁来定、何时前定 |
| **可重复执行** | 相同输入 + 相同规则 = 相同输出，任何 agent 可接手 |
