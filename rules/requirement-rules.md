# 需求文档生成规则

## 生成前：先提问，最多 4 题

收到一句话想法后，检查是否缺以下四类信息，缺哪类就问哪类，**一次性问完，不要来回追问**：

1. **角色分支**——这件事所有角色都能做，还是分角色？（例："寄语墙代录入"是行政专属操作，需要先确认。）
2. **异常/边界路径**——网络失败、内容为空、超出数量限制、重复提交等情况下应该发生什么？
3. **权限边界**——未登录、越权访问、跨活动访问会怎样？
4. **非功能要求**——是否有时限（如审批 SLA）、并发限制、数据量级假设？

四题问完用户可能仍答不全，答不全的部分不要脑补，写入文档「已知缺口」章节，注明谁来定、何时前定。

## 十一个必备章节

`templates/requirement.md` 是骨架，正文必须覆盖以下十一节，顺序固定：

1. 概述——做什么、为什么、不做什么（非目标）
2. 涉及角色——引用 `ROLES.md`，不重新定义
3. 术语与模块归属——用到的术语若未登记，先去 `GLOSSARY.md` 登记
4. 使用场景——按角色列典型场景，不写成 UI 步骤
5. 业务流程与状态机——有状态流转的对象必须画出状态机（文字表格即可，不强制图）
6. 数据对象——业务语义定义，禁止出现字段名/类型（那是接口清单的事）
7. 权限规则——本对象唯一定义处，格式：谁 + 在什么条件下 + 能做什么
8. 校验规则——本对象唯一定义处，格式：字段/动作 + 规则 + 触发时机
9. 页面与状态清单——列出需要原型覆盖的页面，及每页需要的五态中的哪几态
10. 验收标准（AC）——编号 `AC-001`、`AC-002`……每条可独立测试，供 QA 直接派生用例
11. 已知缺口与非目标——未定项写这里，禁止悄悄留白

## 引用而非复述

角色定义引用 `ROLES.md`、术语引用 `GLOSSARY.md`、跨模块约定（分页/时区/金额精度）引用 `background/conventions.md`——用链接或文件名引用，不要把内容抄一遍到本文档里，抄一遍就产生了第二个事实源。

## 载体差异文件

只有当同一条需求在不同载体上确有交互差异时才建 `<端侧>/<载体>/<模块>-<编号>-<端侧>-<载体>.md`，且只写差异部分，不复述 `shared` 已经写过的业务规则。
